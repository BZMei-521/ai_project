# 通用空间预演舞台设计

**日期：** 2026-08-19  
**状态：** 已确认  
**适用范围：** AI 导演工作台的全部分镜项目  
**前置设计：** `2026-08-17-ai-director-panorama-workflow-design.md`

## 1. 背景与问题

现有流程已经把 2:1 等距柱状全景图定义为场景空间的权威视觉来源，并用 `CameraPlan` 记录 yaw、pitch、FOV 和连续性分组。这能稳定机位和背景方向，但不能计算角色、动物、道具的三维坐标、朝向、骨架姿态、接触关系与跨镜状态。

因此，单靠上一镜画面或分镜参考图仍会出现以下漂移：

- 人物姿态在相邻镜头间跳变；
- 人物与道具的握持、接触和左右手关系失真；
- 多角色站位、视线和遮挡关系不连续；
- 室内外、载具、动物和非写实场景缺少统一的空间表达；
- 场景图更新后，旧分镜仍可能引用已经失效的空间信息。

本设计在全景层与分镜生成层之间增加一个“通用空间预演舞台”。系统先从全景或其他环境来源自动初始化轻量三维代理，再由用户修正角色、道具、相机和约束，最后才生成分镜图和视频。

## 2. 目标

1. 在分镜生成前建立可计算、可修正、可版本化的场景空间。
2. 同时约束角色特征之外的姿态、朝向、站位、接触、视线和遮挡。
3. 支持人物、四足动物、道具、载具、建筑、自然环境和抽象空间，不绑定单一故事或单一骨架。
4. 自动初始化失败时仍可用手工代理舞台继续工作，不阻断创作。
5. 复用现有 `PanoramaMaster`、`CameraPlan`、资产管理和 ComfyUI 队列，不破坏已有项目。
6. 在当前本地硬件上稳定运行，并避免三维预览与高显存视频生成争抢 GPU。

## 3. 非目标

- 不建设 Blender、Maya 级完整建模、绑定或动画系统。
- 不要求从单张全景恢复真实尺度和不可见区域的精确几何。
- 不以三维代理直接取代最终生成画面；代理只提供结构、姿态和相机控制。
- 第一阶段不做物理模拟、布料、毛发、群集动画或高精度动作捕捉。
- 不复制灰豆 AI 光影引擎的实现或数据，只借鉴“先建立空间参考，再做分镜”的产品流程。

## 4. 核心原则

### 4.1 混合空间，而非纯全景或纯三维

全景提供权威外观、材质和环境语义；轻量三维代理提供可计算的深度、坐标、遮挡和碰撞。两者通过同一世界坐标系对齐。

### 4.2 自动初始化，人工拥有最终控制权

系统可从全景估算深度和网格、识别地面与主体，并自动放置代理；任何估计都必须标注置信度，允许用户移动、旋转、缩放、重绑和重置。

### 4.3 状态快照是跨镜连续性的权威

每个节拍保存一份 `StageStateSnapshot`。下一镜默认继承上一镜终态，而不是重新从提示词猜测人物姿态与空间关系。

### 4.4 能力检测与渐进降级

每项自动能力都有显式的可用、缺失、运行失败和手工替代状态。缺模型时不得伪装成功，也不得阻止用户建立手工舞台。

## 5. 数据模型

### 5.1 SceneStage

`SceneStage` 是一个场景的空间权威记录：

```ts
type SceneStage = {
  id: string;
  sceneId: string;
  revision: number;
  coordinateFrame: CoordinateFrame;
  environment: StageEnvironment;
  entities: StageEntity[];
  constraints: StageConstraint[];
  cameras: StageCamera[];
  snapshots: StageStateSnapshot[];
  capabilities: StageCapabilityReport;
  sourceDigest: string;
  updatedAt: string;
};
```

`sourceDigest` 由环境源、实体资产和关键配置计算。任何输入变化都会令相关预演输出标记为 stale，而不是静默复用。

### 5.2 坐标系与尺度

`CoordinateFrame` 规定右手坐标系、Y 轴向上、米为单位，并保存世界原点、前向轴、地面平面和尺度来源。自动估算无法确定真实尺度时，必须由一个已知高度的角色、门、道具或用户输入完成尺度校准。

### 5.3 环境来源

`StageEnvironment` 使用可组合来源，而不是硬编码全景：

- `panorama`：2:1 全景纹理；
- `depth_mesh`：由 MoGe 或其他深度方案生成的代理网格；
- `imported_mesh`：用户导入的 GLB/GLTF 轻量场景；
- `procedural`：房间、地面、墙、台阶等参数化代理；
- `cards`：远景、窗外、天空等二维卡片；
- `empty_stage`：只有地面和坐标系的手工舞台。

常规推荐组合为 `panorama + depth_mesh + procedural corrections`。没有全景的项目也能从导入网格或空舞台开始。

### 5.4 实体组件模型

`StageEntity` 通过组件表达不同对象，避免按题材写死类型：

```ts
type StageEntity = {
  id: string;
  assetId?: string;
  label: string;
  tags: string[];
  transform: Transform3D;
  geometry: GeometryProxy;
  rig?: RigBinding;
  attachments?: AttachmentPoint[];
  bounds?: Bounds3D;
  visibility: VisibilityState;
  metadata: Record<string, unknown>;
};
```

- 人形实体使用通用人形骨架和可重定向关节映射；
- 四足实体使用简化四足骨架；
- 道具和载具至少有变换、包围盒与挂点；
- 建筑和自然物可仅有静态几何与语义标签；
- 未知生物可从刚体链或用户定义骨架开始。

### 5.5 姿态与状态快照

`PoseSnapshot` 保存根节点变换、局部关节旋转、接触点和来源。来源分为 `auto_pose`、`previous_snapshot`、`manual` 和 `imported`，并记录置信度。

`StageStateSnapshot` 保存一个叙事节拍的完整状态：实体变换、姿态、可见性、挂接关系、相机、约束求解结果及其前一快照 ID。镜头开始状态引用上一节拍终态，用户明确断开连续性时才新建初始状态。

### 5.6 通用约束图

`StageConstraint` 使用实体 ID、挂点 ID 与参数表达：

- `attachment`：握持、佩戴、乘坐、装入；
- `contact`：脚接地、手扶墙、物体置于桌面；
- `look_at`：人物、动物或镜头视线；
- `distance`：角色间距、道具距离；
- `orientation`：面向、平行、垂直和相对朝向；
- `path`：移动起点、终点和中间点；
- `visibility`：必须入镜、可隐藏、局部可见；
- `occlusion`：前后遮挡关系；
- `count`：群体或重复物数量；
- `axis_limit`：关节或机械部件活动范围。

第一阶段采用确定性校验和简单求解，不引入完整物理引擎。无法满足的约束显示冲突，不自动篡改已确认状态。

### 5.7 相机与既有 CameraPlan

`StageCamera` 扩展现有 `CameraPlan`：保留 panorama yaw、pitch、FOV，同时增加世界坐标 position、quaternion、target、焦距/传感器等价参数、近远裁剪面和 continuity group。

兼容规则：旧项目只有 yaw、pitch、FOV 时，从全景中心生成零平移相机；用户开始三维调度后才写入世界空间字段。

### 5.8 空间渲染回执

每次为分镜生成控制素材时保存 `SpatialRenderReceipt`：

- stage revision 与 source digest；
- snapshot、camera 和 constraint IDs；
- depth、normal、pose、mask、edge 等输出路径与尺寸；
- 所用能力、模型和降级路径；
- 生成时间、随机种子和错误诊断。

回执让分镜可追溯，并能检测“场景已修改但控制图仍是旧版”。

## 6. 工作流

### 6.1 场景初始化

1. 选择或生成 `PanoramaMaster`，也可选择导入网格或空舞台。
2. 运行环境能力预检。
3. 若 MoGe 可用，从全景生成点图、深度和轻量网格；否则进入手工代理模式。
4. 用户校准地面、世界原点、尺度和主要障碍物。
5. 放置角色、动物、道具与载具代理，绑定资产和骨架。
6. 保存 stage revision 1。

### 6.2 节拍与镜头调度

1. 从上一节拍终态继承实体和姿态。
2. 为当前节拍调整角色根变换、骨架姿态、挂点和移动路径。
3. 设置或复用相机，预览构图与遮挡。
4. 运行约束检查；有硬冲突时禁止标记“空间已确认”。
5. 保存 `StageStateSnapshot`。

### 6.3 分镜与视频生成

1. 从确定的 snapshot 和 camera 渲染 depth、normal、pose、mask 与语义摘要。
2. 将控制素材、角色身份参考和场景全景共同注入现有 ComfyUI 分镜工作流。
3. 分镜图通过人物、姿态、空间和镜头连续性检查后，进入现有视频生成链路。
4. 视频结果回写对应回执，不反向覆盖空间权威状态。

## 7. 编辑器体验

空间预演作为 AI 导演工作台中的独立阶段，位于“场景资产”之后、“分镜生成”之前。

主要界面包含：

- 中央无装饰三维视口：全景、代理网格、实体、骨架、路径和相机锥体；
- 左侧场景树：环境层、实体、骨架、约束和快照；
- 右侧检查器：变换、挂点、姿态、相机、置信度和冲突；
- 底部节拍轨道：镜头开始/结束状态及继承关系；
- 顶部工具：选择、移动、旋转、缩放、骨架姿态、相机、吸附和可见层。

所有自动结果都可撤销。状态栏只显示事实状态，如“自动深度可用”“手工代理模式”“3 项约束冲突”，不使用模糊的成功提示。

## 8. 通用场景适配

系统按能力组合工作，不按题材分叉：

| 场景 | 主要环境源 | 实体/约束重点 | 允许降级 |
|---|---|---|---|
| 室内对话 | 全景 + 房间代理 | 视线、坐姿、遮挡 | 手工墙面与地面 |
| 户外行走 | 全景 + 深度网格 | 路径、脚接地、朝向 | 平面地面 + 远景卡片 |
| 多人打斗 | 全景/导入网格 | 骨架、距离、接触 | 简化碰撞体 |
| 骑乘/载具 | 导入/参数化代理 | attachment、路径 | 刚体载具代理 |
| 四足动物 | 任意环境 | 四足骨架、脚接地 | 刚体链姿态 |
| 巨物/微缩 | 任意环境 | 尺度锚点、相机近远裁剪 | 用户手工尺度 |
| 梦境/抽象空间 | 卡片/空舞台 | 构图、相对位置 | 无真实尺度模式 |

无真实尺度模式仍保存一致的相对坐标，但必须在回执中标明 `scaleMode: relative`。

## 9. 本地部署与硬件预算

### 9.1 已核验环境

2026-08-19 的只读检查结果：

- GPU：NVIDIA GeForce RTX 5070 Ti，16,303 MiB 显存，Compute Capability 12.0；
- CPU：AMD Ryzen 7 9800X3D，8 核；
- 内存：约 48 GB；
- C 盘可用空间：约 687 GB；
- Node.js 24.19.0、npm 10.9.2；
- Rust/Cargo 1.97.1；
- WebView2 Runtime 137.0.3296.68；
- Tauri 2、React 18 与现有 node_modules 可用；
- ComfyUI 可从 `127.0.0.1:8188` 访问；
- 已有 360 转换、OpenPose、Depth Anything、Metric3D、Zoe、MiDaS、MoGe 节点接口和网格/深度/法线输出能力。

结论：硬件与基础运行时满足本地开发和生产使用，没有硬件升级前置条件。

### 9.2 缺失的软件依赖

1. 前端尚未依赖 Three.js。实施时新增 `three`，用 React 生命周期封装原生 Three.js 视口；第一阶段不额外引入完整编辑器框架。
2. ComfyUI `LoadMoGeModel` 已存在，但 `geometry_estimation` 模型列表为空。自动空间初始化需要：
   - 文件：`moge_2_vitl_normal_fp16.safetensors`；
   - 目录：ComfyUI 共享模型根目录下的 `models/geometry_estimation/`；
   - 官方蓝图来源：`Comfy-Org/MoGe`。

模型下载和安装属于实施计划中的显式部署步骤；在模型可用前，功能必须显示“手工代理模式”，不得队列一个必然失败的 MoGe 工作流。

### 9.3 资源上限

为避免 16GB 显存峰值冲突，默认采用以下预算：

- 编辑器全景纹理最高 4096x2048，超大源图生成缩略代理但保留原文件；
- 初始 MoGe 全景推理：`split_resolution=512`、`merge_resolution=1920`、`batch_size=1`；
- 自动网格先做简化，视口可见三角面默认不超过 250,000；
- depth/normal/pose 控制图按目标镜头尺寸输出，当前推荐 1344x768；
- 三维视口按需渲染，后台或面板隐藏时暂停；
- ComfyUI 高显存任务开始前释放非必要 WebGL render target 和缓存；
- MoGe 初始化与 MiniMax H3 视频生成禁止并发；
- 预检发现可用显存不足时排队等待或要求用户释放模型，不自动降低到可能破坏质量的未知参数。

CPU、内存和磁盘容量足够。现有运行中模型可能把系统空闲内存压低，因此每次自动初始化和视频生成前都重新读取 ComfyUI `system_stats`，不使用启动时快照。

## 10. 能力预检与降级

`StageCapabilityReport` 至少检查：

- WebGL2 与最大纹理尺寸；
- Three.js 视口可创建；
- ComfyUI 在线状态和端口；
- MoGe 节点与模型文件；
- 360 转换、姿态、深度和法线节点；
- GPU 总量/可用量、系统内存和磁盘余量；
- 浏览器模式与 Tauri 模式的文件访问能力差异。

状态必须逐项记录：`available`、`missing_dependency`、`temporarily_unavailable`、`failed`、`manual_fallback`。任何降级都写入空间渲染回执。

## 11. 持久化与兼容

- 新空间数据独立存储，通过 ID 引用现有场景、镜头和资产；不重写旧资产文件。
- 所有 schema 带版本号并提供纯函数迁移。
- 旧项目打开时不自动生成或修改舞台，用户选择“建立空间预演”后才创建。
- panorama yaw/pitch/FOV 与三维相机互相可转换；出现不可逆信息损失时保留原字段。
- 删除实体或更新资产前检查快照和回执引用，采用软失效标记而非级联删除。

## 12. 错误处理

- 自动几何失败：保留全景，记录诊断，进入手工代理模式。
- 模型缺失：显示准确文件名和目录，不提交 ComfyUI 队列。
- 约束冲突：突出冲突实体和约束，不静默选择其中一个。
- 来源变更：相关快照或回执标记 stale，用户确认后重新生成。
- WebGL context lost：保存未提交编辑，重建视口；三维失败不得损坏项目数据。
- 生成取消：只清理本次运行专属临时目录，保留正式资产和失败回执。

## 13. 测试策略

### 13.1 纯逻辑测试

- schema 解析、版本迁移和旧项目兼容；
- 坐标变换、全景角度与三维相机互转；
- 快照继承、分支和 stale 传播；
- 约束校验与冲突报告；
- 能力矩阵和降级决策；
- source digest 与回执可追溯性。

### 13.2 视口与交互测试

- WebGL 初始化、context lost 恢复和资源释放；
- 实体选择、变换、骨架操作、挂接与撤销；
- 4096x2048 全景、250k 三角面和多个实体下的稳定帧率；
- 桌面和最小支持窗口尺寸下无控件遮挡。

### 13.3 ComfyUI 集成测试

- 离线、节点缺失、模型缺失和显存不足均有确定性结果；
- MoGe panorama -> mesh/depth/normal 工作流结构审计；
- 控制图尺寸、快照 ID、stage revision 和回执一致；
- 自动初始化与 H3 视频任务串行调度；
- 取消和失败仅清理本次运行目录。

### 13.4 场景验收矩阵

用第 8 节七类场景各建立最小样例。每个样例至少验证两镜继承、一次相机变化、一个挂接或接触约束、一次人工修正和一种降级路径。

## 14. 分阶段交付

### 阶段 A：数据底座与只读视口

建立 schema、持久化、能力预检、Three.js 视口、全景球和手工基础代理。

### 阶段 B：实体、骨架与快照

加入通用实体组件、人形/四足骨架、道具挂点、状态快照和节拍继承。

### 阶段 C：自动环境初始化

安装并接入 MoGe 模型，生成深度/网格/法线，完成尺度和地面校准、网格简化及手工修正。

### 阶段 D：约束与控制图

实现约束图、冲突检查、相机控制图渲染和 `SpatialRenderReceipt`。

### 阶段 E：分镜链路集成

把空间控制素材接入现有角色一致性和分镜生成流程。先用《从一根木矛开始的文明》10 秒开场做纵向验证，再执行七类场景通用验收。

## 15. 验收标准

1. 没有 MoGe 模型时，用户仍能从空舞台或全景手工完成空间预演。
2. 相邻镜头默认继承人物/动物姿态、道具挂接、站位和相机连续性。
3. 修改场景、资产或舞台后，旧控制图明确标记 stale。
4. 七类场景均使用同一核心 schema 和约束引擎，不出现题材专用数据分叉。
5. 当前硬件上编辑器视口和 ComfyUI 高显存任务通过串行调度稳定运行。
6. 任何自动降级、失败和模型缺失都有可复现诊断与回执。
7. 现有项目可无损打开，只有用户主动建立空间预演时才产生新数据。
